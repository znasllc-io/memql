# One Email app Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fold Campaigns into one MemQL OS Email app (Overview, Campaigns, Automations, Audiences, Templates with its Layouts view, Inbox, plus Settings and Logs) where every Add runs the kit `Wizard`, every record page carries one `ActionBar`, automations are drawn and edited as a vertical Flow (by hand or by "Describe it instead"), and every audit defect in the old Email and Campaigns screens is fixed without losing a capability.

**Architecture:** `clients/os/src/apps/email/` becomes the only mail app: one manifest (`id: "email"`, icon `Mail`), one resource family (`app:email`, `app:email/inbox`, `app:email/logs`), one settings store. Five root live feeds (campaigns, audiences, templates, senders, rules; journeys join in Task 14) walk every page and are retained once; per-record reads (series, testing settings, signup forms) are composed into one subscription per concept; on-demand reads (stats, ledgers, rosters, counts) refresh through the kit `AutoRefresh`. Each section is a list page (`Head` + `Refine` + `AddButton` + `LiveList`/`RecordRow`) whose rows open a record page that replaces the list (rule 11) and carries one `ActionBar` computed by a pure `acts` function. Adding runs `Wizard`. Organization email layouts (saved in VS Code) live inside Templates as a sibling view behind `LocalTabs`, read through `emailLayouts` and archived or restored through `campaignSaveLayout`. The automation `Flow` is the app's one bespoke visual: a pure step model (`flow.ts`) and a thin keyboard-reachable renderer (`Flow.tsx`).

**Tech Stack:** React OS client (`clients/os`, vitest + Testing Library), the OS kit (`clients/os/src/kit`), the generated TS SDK (`sdk/ts/src/client`), MemQL DSL (`dsl/rbac/seeds.memql`, two `dsl/campaigns` constructs in Task 2), Go (the RBAC mirror and the organization-app mapping in `component/auth`, `component/memql`), the browser QA harness (`clients/os/qa`).

**Spec:** `docs/superpowers/specs/2026-10-11-email-layouts-automations-design.md`, section 3 (the Email app), the UI-facing parts of section 4 (journeys, double opt-in, link pages are server-side), section 5's E4 and the OS bullets of section 7. Read it first. The builtin, query and copy names come from the two engine plans in this directory: `2026-10-11-email-layouts-engine.md` (`emailLayouts`, `emailRender`, `campaignSaveTemplate` with `document` / `sourceArtifactId` / `restore` / `issues`, `campaignSaveLayout`) and `2026-10-11-email-automations-engine.md` (`journey`, `journeyEnrollment`, `campaignSaveJourney`, `campaignSetJourneyState`, `campaignDescribeJourney`, `journeys`, `journeyById`, `journeyEnrollmentCounts`, `setAudienceConfirmation`, the issue and refusal copy tables, E4's OS lines in its Task 16).

**Tracking:** sub-project #6033 (program epic #6022). Every commit references #6033.

## Global Constraints

- Pre-release: no compatibility shims, aliases or migrations of client state. The `campaigns` app id, the `app:campaigns*` resources and the `memql-os-campaigns-v1` browser key are deleted, not aliased. Stored grants that name `app:campaigns` become inert (Ruling 1).
- Stage files by explicit path (`git add <file>`; `git mv` for moves), never `git add -A` or `git add .`. Write each commit message to a file in your scratchpad and `git commit -F <file>`; end it with the attribution line your session requires. Another session may commit in the same worktree: if `git commit` reports `index.lock`, wait a few seconds and retry.
- Clients use bare ids only. Never compose, split or compare canonical ids. Layout ids (`builtin:<name>`, `org:<id>`) are opaque strings the server issues; the OS only displays the name `emailLayouts` returns for them.
- The OS interface language is binding: `clients/os/DESIGN.md` (all twelve rules, "One wizard for adding", "Record lists", "Loading is the shape of the content", "App overviews", "A tab is a different kind of thing", "One trail row"), `clients/os/SUPERVISED-VISUAL-COMPOSITION.md`, `.agents/skills/memql-ui-design/SKILL.md`. In particular: an act that is not legal is absent, never disabled; acts that change a record live only in its `ActionBar`, at most three, primary last, ways out as `Act.text`; a list and its page never share a scroller; loading is a skeleton, never a caption; a refusal is the engine's sentence, verbatim, in place.
- Copy: sentence case, no emojis, says what happened and what to do, no developer voice, one word per thing (Ruling 6). The exact strings in this plan are the contract; tests assert them. Engine sentences (issue texts, refusals) are rendered verbatim, never paraphrased.
- One subscription per concept (the Packages rule): no two live collections over the same concept may be mounted at once. Recipient, delivery, engagement and enrollment rows are routing exclusions, so their reads are bounded on-demand reads refreshed by `AutoRefresh` while visible.
- Cross-node: the OS assumes nothing about which node answers. Every write is retry-safe through a caller-generated id held for the life of the flow (campaign, audience, journey, test request); nothing is inserted locally, rows arrive on the live feeds.
- No new HTTP. Every read and write goes through the generated SDK methods on `connection.query`.
- Tests live under `clients/os/test/email/` (plus the shared suites a task names). Each task is test-first. Shared test helpers live in `clients/os/test/email/harness.tsx` (moved from `test/campaigns/harness.tsx` in Task 1).
- Per-task checks: `cd clients/os && npm run typecheck && npx vitest run test/email` plus the suites the task names. When the registry or a section list changes: `cd clients/os && MEMQL_UPDATE_NAVIGATION=1 npx vitest run test/ask/navigationContract.test.ts`, commit `component/memql/os_navigation.json`, then `make platform-graph && go test -count=1 -run TestPlatformGraph .` and commit `component/architecture/embedded/platform.graph.json`. When seeds or `requires:` change: `go test ./component/memql/ -run TestOsRegistryRequiresMatchTheAppSeeds -count=1` and `go test ./component/auth/ -run TestSeedMatchesCompiledMirror -count=1`. When any Go or DSL file changes: `go test -count=1 .` at the repo root.
- Fresh worktree setup, once: `make identity-tailwind`; `cd sdk/ts && npm ci && npm run build`; `cd clients/os && npm ci`. Disk is tight: never run `npm ci` in two worktrees at once, and remove `node_modules` from scratch worktrees when done.
- `clients/os/qa` is not type-checked by `npm run typecheck`. Whenever a task touches `qa/` or moves a module `qa/main.tsx` imports, prove it still bundles: `cd clients/os && npx vite build --config qa/vite.config.ts --outDir "$SCRATCH/qa-build" --emptyOutDir`, where `$SCRATCH` is your session's scratchpad directory (never a path inside the repository).
- Do not run docker, do not touch a cluster, do not deploy. Screenshots (Task 20) are written under the scratchpad, never the repository.
- Engine dependencies are named per task. A task that names an engine plan's task must not start until that task is merged into this branch (its generated SDK methods are what `npm run typecheck` compiles against).

## Rulings

Decisions this plan makes where the spec is silent or had to bend. Each is binding on the tasks below.

1. **One app, one resource family.** App id `email`, name "Email", icon lucide `Mail`. `app:email` (all five roles), `app:email/inbox` (owner, developer) and `app:email/logs` (owner, developer, admin) are already seeded; the eight `app:campaigns` and `app:campaigns/logs` seed rows and their two mirror entries are deleted. `organizationApp("v1:campaigns:*")` answers `app:email`, so journey and layout concepts follow automatically. Grants stored in a database that name `app:campaigns` are not migrated (spec section 3: "no alias"); an owner re-grants `app:email` in Users. The commit body says so.
2. **Tabs are nouns.** Tab order: Overview, Campaigns, Automations, Audiences, Templates, Inbox; Logs and Settings stay header icons. Senders and Rules are no longer tabs: senders live in Settings, rules are automations. Automations keeps Rules' `needs: ["email", "campaigns"]`; Inbox keeps `requires: "app:email/inbox"`.
3. **Inbox on a non-capture cluster.** No engine fact distinguishes a capture cluster at tab-gating time, so the tab stays for owners and developers and its body says `Nothing is captured on this cluster.` / `This cluster delivers email to real inboxes.` (spec deviation, reported).
4. **Settings is grouped by scope.** Head "Settings"; one `Organization` field, shown only when the person can choose, scopes Sending domain, Senders, Testing and Package; Preferences come last because they are not per organization. This reorders the spec's list (Sending, Testing, Preferences, Package) and removes the old page's three organization pickers (audit D2, B3).
5. **Preferences.** `includeArchived` (Switch "Include archived"), `trackByDefault` (Switch "Track opens and clicks"), `defaultSection` (Select "Opening tab", offering only tabs this person can open, never Logs or Settings). Store key `memql-os-email-v1`. Finished campaigns are no longer hidden by a preference; they are a `Status` facet in Refine (a subset is a question, rule 2). Paused rules are never hidden (audit C2).
6. **Vocabulary (`apps/email/words.ts`).** organization, audience, template, sender, archived. State words: campaign `Draft, Scheduled, Sending, Paused, Sent, Cancelled, Failed`, a repeating source `Repeating, Repeating paused, Repeating stopped`; template `Draft, Published, Archived`; audience, sender and organization layout `Active, Archived`; a built-in layout carries no state word (its fact reads `Built in`); automation `Draft, On, Paused, Retired`; rule `Draft, On, Paused, Refused`; subscriber `Subscribed, Pending, Unsubscribed, Bounced, Reported spam`; delivery `Sent, Skipped, Failed, Not yet sent`. One sentence for unset sending: `Sending isn't set up for <organization>.` with the engine's reason as detail. One pointer to setup: the in-app Settings (an `Open Settings` link), and for cluster email `Settings → Connections → Email` (owners and developers only).
7. **Campaign page acts** follow the spec table, with four additions that keep shipped capabilities: (a) `Send a test` (text) is offered in every state the engine accepts a test (draft, scheduled, sending, paused, sent, cancelled, failed), because `campaignTestAudienceSend` "works in every source lifecycle"; (b) a draft's primary follows its saved time: `Send now` with no time, `Schedule` with a future one; (c) a draft that sources a series reads `Repeating` / `Repeating paused` / `Repeating stopped` with `Pause` / `Resume`; (d) cancelling a draft is the danger text act `Cancel campaign` in its Edit page's bar (the spec's draft row has no room for it). `Edit` is offered for drafts and repeating sources only (scheduled campaigns follow the spec: Cancel or Send now).
8. **Add a campaign.** Name lives on Review (placeholder = the template's name). Two Switches on Review, `Count who opens it` and `Count who clicks a link`, default to the tracking preference. Reply-to is set on the Edit page only. `Save as draft` keeps an intended Schedule time (`createCampaign.scheduledAt`); a Repeat choice cannot be stored on a draft, so Save as draft saves the campaign without it and the bar says `A draft doesn't repeat until you start it.`. On Review the floor is `Send a test` (text), `Save as draft` (text), primary; the way out before anything is written is the trail's Back. Once a draft exists (after a test or a refused send) the floor is `Cancel` (text, asks by name, cancels the draft), `Send a test` (text), primary.
9. **Create new template** opens the VS Code New email page through a new resource kind, `memql-file://<domain>/new-email/<bareAccountId>/New%20email` (three path segments, no query), byte-identical to the VS Code plan's `newEmailResource(domain, accountId)`; that plan teaches its validators the kind. The spec's `.../new/email?account=...&returnTo=email` form is superseded because it does not fit the resource grammar. Publish in VS Code never asks for the organization (the editor resolves it before the first preview), so a new published template in the chosen organization is the signal. The wait is client-side over the live templates feed: it resolves on a template id that was not in the organization's templates when the wait began; the campaign wizard waits for it to be published, the Templates wizard opens it whatever its state.
10. **Test sends.** To the organization's testing audience when one is set (`campaignTestAudienceSend`, request-id recovery), otherwise to the person's own address (`access.primaryEmail`, `campaignTestSend`, which accepts a draft template and reports `unresolvedTags`), otherwise absent.
11. **Two engine constructs the OS needs and no engine plan adds** (spec gap, reported): `restoreAudience` (the spec's audience Restore) and `audienceSubscriberCount` (the spec's "subscribers"; `audienceRosterSize` counts everyone, including pending and unsubscribed people). Task 2 adds both, DSL-only, mirroring `archiveAudience` and `audienceRosterSize`. If the controller moves them into an engine plan, Task 2 becomes a dependency instead.
12. **Audiences.** Adding people (a CSV or one address) is one Wizard, `Add people`. A confirmation change is a bar act (`Ask people to confirm` / `Stop asking to confirm`, text, asks first with its consequence). A signup form is connected through a Wizard and has its own page carrying the form HTML as a `CopyField`.
13. **Automations.** A journey's Retire is `campaignSetJourneyState(archive)`: terminal, asks first. A rule's Retire is `campaignRetireEmailRule` (the rule stays, paused, its generated automation removed). A Flow is editable only in Draft or Paused, for journeys and rules alike (an On rule is paused before editing, matching `Pause the automation before editing it.`). Unsaved edits replace the acts with `Discard changes` (text) and `Save` (primary); `Turn on` is absent until the edits are saved and nothing blocks it.
14. **The OS mirrors the engine's issue table** (automations plan Task 11) in `automations/issues.ts`, with the same texts, to decide what to offer and to mark cards; the engine stays authoritative and a refusal it returns is shown verbatim. A test pins the texts.
15. **Flow counts** (no per-person enrollment read exists for clients): Trigger = all enrollments; a Confirm card = enrollments `waiting` at its id; a Wait pill = `active` enrollments whose next step is the step after the wait (people sitting out the wait); a Send card = none (sending is instantaneous); End = `completed`, plus `left early` (`exited`) and `failed` when non-zero. Exit-reason codes are therefore not shown (reported).
16. **Describe it instead: Check it saves.** The engine has no dry run, so `Check it` is `campaignSaveJourney` creating one draft under a journey id held by the page and updated (with its revision) on a later check. `Edit as steps` continues in the wizard before a check and on the saved draft's page after one.
17. **Event rules in the wizard** ask, one per step: What (search + choices from `listConcepts`), When (created or changes), Only when (condition, optional), Who (mode, then roles, audience or field), Template, Sender (absent for "People in this cluster", which never uses a sender; audit C1), Review (Name).
18. **Record destinations for search and Ask:** `campaigns.campaigns` (`campaignId`, `["name"]`), `campaigns.audiences` (`audienceId`, `["name", "description"]`), `campaigns.templates` (`templateId`, `["name", "subject"]`) in Task 5, `campaigns.journeys` (`journeyId`, `["name", "description"]`) in Task 14. The app consumes `{campaignId}`, `{audienceId}`, `{templateId}`, `{journeyId}` intents by id and opens the page, whichever tab was showing.
19. **Retained panes** (Fleet's pattern): a visited section stays mounted and hidden, so wizard answers and unsaved edits survive tab switches, and a step's floor act that leaves for another tab (`Add an audience`, `Set up sending`) comes back to the same wizard.
20. **Kit promotions** (second or later use): `DateTimeInput`, `TextArea`, a `Subhead` `actions` slot, and `LiveList` `errorContent` with an optional `emptyText`. Nothing else is promoted.
21. **Preview isolation with styles.** `apps/email/preview.ts` keeps inline styles, `<style>` blocks and table attributes, drops every CSS declaration that loads anything (`url(`, `@import`, `expression(`, `behavior`, `-moz-binding`), strips scripts, handlers, forms, `meta`, `base`, `link` and non-raster sources, and carries a CSP meta with `default-src 'none'; style-src 'unsafe-inline'; img-src data:`. The frame keeps `sandbox="allow-popups allow-popups-to-escape-sandbox"` (no scripts, no same origin).
22. **Overview figures.** Sent, 30 days = sum of `sentCount` over campaigns whose `startedAt` is within 30 days. Open and click rates = unique opens (clicks) over sent, summed across those campaigns that tracked opens (clicks), from `campaignStats`; absent when any contributing unique figure is unmeasured, or when no campaign in the window tracked it. Subscribers = sum of `audienceSubscriberCount` over active audiences. Active automations = journeys `active` plus rules `active`. Absent is never zero.
23. **Data reads.** The five root feeds walk their cursors (today they stop at the first 50). Series, testing settings and signup forms are each one composed feed (one subscription) over the ids in view. `useReading` loses its private timer; visible surfaces mount `AutoRefresh` (5 s) beside the reading so hidden panes, hidden tabs and offline windows stop reading.
24. **Layouts live inside Templates** (controller addition): `LocalTabs` `Templates` / `Layouts` directly under the Templates Head (sibling views, not a new tab). The Layouts view lists the four built-ins once (deduplicated by `id`), then each organization's layouts, from one `emailLayouts({ accountId, includeArchived: true })` reading per organization in view (the same reading names a template's layout, so no second read; archived layouts listed only with `Include archived`). It has no Add: layouts are saved from a finished email in VS Code. A layout's page previews it through `emailRender`; built-ins have no acts and no bar; an organization layout's bar offers `Archive` (text) or, archived, `Restore`, through `campaignSaveLayout({ layoutId, accountId, name, document, expectedRevision, action })` with the exact revision from `emailLayoutById` (layouts plan Rulings 15 and 16; the stored name and document are passed back unchanged, which the engine ignores for these actions). Built-in and organization layout ids are opaque: the OS displays them through the names `emailLayouts` returns and never builds one.

## Design plan

The `frontend-design` process (plan, review against the brief, build, critique) applied inside the MemQL kit and palette. The owner's brief: minimal, clean, every element has a reason, no capability lost. Boldness is spent in one place, the automation Flow.

**Subject.** A mail room for the organizations an operator works for: who gets mail (audiences), what it says (templates, written in the editor), when it goes (campaigns), what happens on its own (automations), and proof (results, the capture inbox).

**Tokens (no new colours).** `--os-ground` window, `--os-plate` panels and Flow cards, `--os-ink` text, `--os-muted` quiet text and counts, `--os-line` hairlines, `--os-accent` / `--os-accent-soft` selection, the live state and the Flow spine, `--os-rail` the spine at rest, `--os-warn` issues, `--os-error` refusals.

**Type.** `--os-font` everywhere; `--os-font-display` only inside the Flow, for the trigger's audience name and each email's template name; `--os-font-mono` for addresses and conditions. Kit sizes only.

**Layout.**

```
List page                                   Record page (replaces the list)
Campaigns          12   [search] [+]        Campaigns > August update
send  August update   Newsletter  Sent      Audience  Newsletter (link)
send  Welcome series  Signups     Draft     Template  Welcome 2 (link)
                                            Results / Breakdown / Who got it / Tests
                                            ------------------------------------------
                                            Sent                    [Send a test] [Duplicate]

Automation page, wide (>= 760px pane)                     narrow: inspector folds under the card
Automations > Welcome series
o  When someone joins  Newsletter        214 enrolled | Send
|                                                     | Template [Welcome 2   v]
+-[mail  Welcome 1, then wait for confirmation]       | Sender   [news@acme   v]
```

**Principles.** (1) The Flow is the one memorable thing: one spine, emails hang off it, time sits on it. (2) Everything else is the kit, quiet: lists, pages, wizards and settings look like Deployables and Fleet. (3) State in words, acts in the bar, absent never disabled. (4) Loading is shape; a refusal is the engine's sentence. (5) One word per thing.

**Review against the brief** (what the first plan had, and why it changed):
- A left-to-right flow canvas with pan and zoom, like the Deploy map. Rejected: a generic node graph, unusable at 520px, and the spec asks for a vertical spine; keyboard reach is simpler in a list-shaped flow.
- Coloured chips per step kind. Rejected: the SaaS-card default. A kind is carried by one glyph and the card's sentence.
- Waits as cards like emails. Changed: a wait is a pill on the spine showing its duration, so time reads as part of the line and emails stay the only cards.
- An Overview with activity sparklines. Rejected: no time series exists (DESIGN "App overviews"); five measured figures and the current campaign distribution.
- A Senders tab. Rejected per spec: setup belongs in Settings.
- A coloured "Proposal" badge. Changed: a proposal is a dashed spine and the word `Proposal` in the bar's state (supervision: proposed vs real told apart by text and form, not colour).

**Copy rules.** Verbs that say what happens: `Add a campaign`, `Send now`, `Schedule`, `Start repeating`, `Send a test`, `Save as draft`, `Turn on`, `Pause`, `Resume`, `Retire`, `Archive`, `Restore`, `Create new template`, `Open in editor`, `Describe it instead`, `Draft it`, `Check it`, `Edit as steps`. An act keeps its name: `Turn on` gives `On`, `Publish` gives `Published`, `Add a campaign` gives "was not added". No visible `Loading` (a skeleton's screen-reader label may say it), no `Updates automatically`, no report-age paragraphs, no explanation of machinery.

**Critique protocol** (Task 20): every scene at 1400 and 520 wide, light and dark. One `Head` per scroller; acts only in the bar; no disabled control; skeletons not captions; focus visible; the Flow reads top to bottom without the inspector; and one "remove an accessory" pass per surface, recording what was removed or that nothing could be.
