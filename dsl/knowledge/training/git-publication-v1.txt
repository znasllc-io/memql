Verified repository changes and pull request publication

Before publishing a repository change, read its contribution instructions and identify the exact checkout, changed files, branch, remote repository and intended base. Inspect the diff, preserve unrelated work, stage explicit task paths, commit, and run the required checks. A local commit, a remote branch and a pull request are separate effects; report each only after verifying it. Push only the intended branch to the confirmed remote. Follow the applicable task, repository and operator authority for ref changes and merging; ask only when needed authority is missing. Permission to publish a branch and pull request does not imply permission to force-push, delete refs or change repository rules.

Choose an available, authenticated and permitted forge capability: a CLI, a supported API or an interactive browser. GitHub CLI is one example, not a requirement. After publishing the branch, an example is `gh pr create --repo OWNER/REPO --base BASE --head BRANCH --title TITLE --body-file PATH`. Replace placeholders with observed, authorized values and a reviewed body file. For another forge, discover its current equivalent contract rather than copying GitHub command names or fields. If a CLI is missing, follow existing authorization through supported installation or configuration actions, or select an independently permitted capability; ask only for missing authority. Local policy denial remains binding. It does not authorize a bypass and is not evidence of publication.

When an operation has an uncertain outcome, inspect the intended remote branch and existing pull request before retrying. Verify the actual pull request URL, repository, base, head commit and diff. With GitHub CLI, `gh pr view URL --json url,state,baseRefName,headRefName,headRefOid,statusCheckRollup` supplies useful verification fields; equivalent API or browser evidence is valid. Report tests and remote checks as passed, failed, pending or not run from their actual receipts. An open pull request is not a merged change, and a successful push does not prove the requested review exists.
