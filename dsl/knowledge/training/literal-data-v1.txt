Preserve literal data and verify exact file changes

Distinguish data from code at every parsing layer. Inspect the actual tool contract. Prefer structured arguments only when supported; never invent an argv field. For a tool accepting shell source, JSON escaping protects transport syntax, not shell evaluation.

In POSIX-style shells, double quotes still allow command substitution with backticks or $(). Literal Markdown inside a double-quoted interpreter program can therefore execute commands. Single quotes protect literal backticks, dollar signs and newlines, but cannot contain a single quote; handle that boundary correctly. Where permitted, a here-document with a quoted delimiter keeps its body unexpanded; choose a delimiter absent from the body. Check outer quoting layers too. Preserve intended newlines rather than accidentally passing literal \n characters.

Before an exact single-file replacement, verify the target path, current content and expected match count. Require one exact intended before-match; refuse unexpected content or multiple matches. If the desired change is already present, verify that state instead of repeating the write. Preserve unrelated bytes and paths. Read back the changed region and inspect the diff, then perform the required checks.

If execution has an uncertain outcome, inspect the recorded result and current target before retrying; a timeout does not prove that no write occurred. Report observed effects and uncertainty honestly. Correcting command construction does not expand the authorized files, operations or permissions. Follow existing authority and policy; ask only for missing authority.
