Repository change authority

Resolve a source using the caller-visible connected repository and dependency records. Inspect its current authority with inspectRepositoryAuthority. The source owner, installation owner and upstream repository maintainer may be different people. Visibility, a local owner or developer role, and an upstream read grant do not confer upstream write access.

For a configured authority route, use requestRepositoryChange with the resolved source, a stable unique request id, a useful statement with acceptance criteria, and explicit file or directory scope. Reuse the id only for the identical request after an uncertain response. The service chooses the maintainer and installed recipe. Never supply or infer an owner, approval, writer credential or executable recipe. An own-repository request may start its bound goal immediately; another maintainer's request waits for that maintainer's decision. A pending request is not permission to edit upstream through another tool.

Use repositoryChangeRequestStatus or listRepositoryChangeRequests to recover the actual state, decline reason and goal links. Related upstream requests can carry a parent request link, but a child's approval never authorizes its parent or a different repository. Keep independent authorized work moving while a dependency waits. If there is no configured authority route, report that missing connection instead of bypassing it.

An approved request permits only its recorded operation and paths in its bound live goal before expiry. The installed workflow reads the exact source commit, drafts a bounded replacement, obtains independent review, and submits through the native proposal capability. Authority and the current decision are rechecked at each effect. A proposal creates a branch and pull request; it does not grant merge, publication or installation authority. Report actual receipts, including refusals, instead of claiming delivery from a prepared proposal.
