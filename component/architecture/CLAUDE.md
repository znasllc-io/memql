# Architecture Framework

**Purpose:** Hold two generated graphs of the system and the schema they are written in. The **architecture model** is the code (services, packages, types, methods, the automation trigger graph), extracted from the Go source. The **platform graph** is what that code is deployed as (roles, Deployments, gRPC services, the front door, routing, concepts, automations, OS navigation), written by `cmd/platformgraph`. Both are embedded for the docs generators and the OS's Cluster map, and share their ids with `component/observe` and `v1:cluster:nodeType.codeReference`.

**Language:** Go (stdlib + `golang.org/x/tools`, no third-party renderers)

**Companion runtime:** `component/observe/` -- the per-invocation capture layer keyed by the same FQNs this framework produces.

**Embed point:** `embedded/topology.model.json` (from `cmd/memql-arch`, via `make arch-model`) and `embedded/platform.graph.json` (from `cmd/platformgraph`, via `make platform-graph`), both baked into every binary that imports `component/architecture/embedded`.

---

## Why this exists

The docs and the OS need to show "what's in this system" at every level of zoom -- cluster, role, service, package, type, method. Hand-maintained diagrams drift; commercial diagram tools couple us to a renderer. The Go toolchain (`go/ast`, `go/types`, `golang.org/x/tools/go/packages`, `.../callgraph`) gives everything the code side needs from the source alone, and the platform side is read from the tree's own declarations (`component/node`, `deploy/k8s`, the proto descriptors, the DSL). This package is the schema and the embedded result: source -> typed graph -> on-disk JSON -> embedded asset -> docs diagrams and the Cluster map.

The framework is intentionally **build-time**, not runtime. The model is a property of a commit, not of a running process. That matches what users expect when they look at a diagram ("this is the code as it is now") and gives the model the same versioning guarantee as any other source file.

## Diagrams supported

C4 + UML, mapped 1:1 onto Kind / EdgeKind in `model/model.go`:

| Diagram | Reads from the model |
|---|---|
| **System context (C4-L1)** | `KindCluster` + its `EdgeContains` services; the platform graph's roles, front door and database |
| **Container (C4-L2)** | `KindService` (the module and each node role) + `EdgeDependsOn`; the platform graph's `runs_on` / `serves` / `dials` |
| **Package / dependency graph (C4-L3)** | `KindPackage` + `EdgeImports` (within a service) |
| **Class diagram (C4-L4)** | `KindType` + `KindInterface` + `EdgeHasField`, `EdgeEmbeds`, `EdgeImplements`, `EdgeContains` (method children) |
| **Sequence diagram** | Walk forward from an entrypoint over `EdgeCalls` (`memql-arch --calls`; not in the committed model) |
| **Call graph / dependency graph** | `EdgeCalls` from an on-demand build; the committed model has none |
| **Automation trigger graph** | `KindAutomation` + `EdgeTriggers`, with strata, filters and loop bounds |
| **Activity diagram / flowchart (CFG)** | (Planned) `golang.org/x/tools/go/cfg` per-function |
| **State diagram** | (Planned) annotation-driven, via doc-comment hints |
| **ERD** | The platform graph's `concept` nodes and `relates` edges, per `namespace` |
| **Deployment diagram** | The platform graph's `deployment`, `k8sService`, `runs_on`, `selects`, `dials` |

Both graphs are **renderer-agnostic**: a docs generator writes a graph -> text translation (Mermaid, design record D6, memql#5728); the OS's Cluster map lays the platform graph out itself.

## ID format

Every entity gets a stable, format-deterministic ID (`model.ID`). The format is documented in `model/model.go` and the constructors in `model/ids.go` are the single source for assembling them -- including the platform graph's (`DeploymentID`, `HostID`, `ConceptID`, ...). A node role is `service:<type>` in BOTH graphs, a package `pkg:<path>`, an automation `automation:<name>`. The format matters because the same string is the join key used by:

- The two graphs themselves (a role's packages in the platform graph are packages of the model)
- `component/observe`'s per-FQN level cache (which method to capture at what verbosity)
- The `code_invocation` hypertable's `code_reference` column (which method produced this row)
- The `v1:observability:codeProfile` concept's `codeReference` field (live config override)
- The `v1:cluster:nodeType` concept's `codeReference` field (cluster node <-> code service link)

If you need to construct an ID from outside the model package, call the constructors; never inline the format string.

## Per-module `arch.yaml`

Each module's root may carry an `arch.yaml` declaring its service identity, descriptions, explicit cross-service edges that the import graph can't see (gRPC peers, queue handoffs, etc.), and the node **roles** it builds. Schema lives in `extract/archyaml.go`; a missing file is fine -- the loader defaults to the directory base name and `./...` roots.

Each declared role becomes a service of its own (`service:<name>`, depending on the module's service). The role set is `component/node/roles.go`; this package is base tier and cannot import it, so memql's root `arch.yaml` carries a copy that `component/node/roles_test.go` holds to the table field for field. Editing `arch.yaml` is the canonical way to change the model's L1/L2 labels.

---

## The runtime side: `component/observe`

The architecture framework gives you the static map; `component/observe` is the runtime layer that emits per-invocation data keyed by the same FQNs. The two were designed together -- if you change the ID format here, the per-FQN cache in observe and every join on `codeReference` need to move with you. See `component/observe/CLAUDE.md` for the runtime story.

## How to use

### Regenerate the model after code changes

```bash
make arch-model
```

**This is the only supported way** (memql#2844). The flag set is load-bearing
and lives in exactly one place, the `arch-model` target:

- **The committed model is STRUCTURAL** (memql#5727, owner decision 7). The
  CHA call graph was 63.9 of the file's 81.3 MB with no consumer, so the
  target leaves `--calls` off: about 17 MB, 34k nodes and 36k edges.
  `make arch-model ARCH_MODEL_CALLS=1` adds `--calls` -- the drift gate's on-demand
  build, never the artifact's, and `TestCommittedModelHasNoCallGraph` pins it.
- `--reproducible` blanks `generated_at` and the absolute workspace path, and
  `--cluster memql` pins the cluster node's name, which otherwise comes from
  your checkout's FOLDER name. Without these the output differs on every run
  and on every machine, and `TestArchitectureModelIsNotStale` fails for
  everyone but you.

`go generate` in `embedded/` now shells out to this target, so the two cannot
disagree. Regenerating by hand is not supported; there is no shorter form that
produces the committed artifact.

Wall time is ~6s on the full workspace (~8s with the call graph), warm.
Regenerate it LAST in any change that touches Go, since the model describes the
code. (Test-only changes need no regeneration -- all three extractor passes set
`Tests: false`.)

**A Go toolchain bump also invalidates it.** The model encodes stdlib-derived
facts -- promoted methods from embedded stdlib types, `implements` edges against
stdlib interfaces, signatures rendered with stdlib type names -- so a minor or
patch bump can move them. CI pins `go-version`, so this bites exactly on the PR
that raises it: regenerate there.

`make arch-model-check` verifies the committed model matches the code. It
builds the call graph on demand, as the gate does wherever the full Go suite
runs; in ci.yml's docs-only gate-inputs step (`RUN_GATES=true`) the gate skips
that build and checks the structural model alone. With the call graph built,
the gate also checks it against the structural pass of the same regeneration
(`callGraphIsConsistent`) and holds it to a floor.
`component/architecture` is its own workspace module (its own `go.mod`,
listed in `go.work`), so a bare `go test ./...` from the repo root does not
run `TestArchitectureModelIsNotStale` -- the same module-boundary gap the
root CLAUDE.md's Testing section documents for `component/memql`. Run the
check from inside `component/architecture/`, or use `make arch-model-check`.

**What "matches" means, precisely.** The gate is a SUBSET check, not a byte
comparison -- every symbol the committed model *references* must still exist in
a freshly regenerated one. It deliberately ignores symbols that exist in the
code and not yet in the artifact, because concurrent merges only ever add them
and a gate that fails on someone else's merge is unwinnable under a merge queue
(memql#2844).

"References" covers **node ids and edge endpoints** (memql#3050) and, since
memql#3288, **the edge set itself**. Three consequences, each a
model-affecting change the node set alone would not show:

- **A deleted symbol an edge still names** -- the #3050 check. It was written
  for `calls` edges into deleted unexported functions (PR #3033 left 33); with
  no call graph committed, the edges it now guards are the structural ones, and
  an unexported package-level function is no longer anything the artifact
  claims. An unexported METHOD of a modelled type is a node, so deleting one is
  caught as a stale node.
- **A relationship that no longer holds between two surviving symbols** -- an
  import, a containment, an implements, a trigger (#3288; measured when it
  landed as 15 stale `calls` edges, every endpoint alive).
- The gate reports what the regeneration no longer mentions, not what you did,
  so a deletion, a rename and a moved relationship all read alike. All want the
  same fix: regenerate. Do not go hunting for a deletion that is not there.

**What the gate still cannot catch, deliberately** (memql#3288):

- **Anything ADDED.** Every check walks the committed model and asks whether
  the regeneration agrees; nothing walks the regeneration. The add-only
  asymmetry is load-bearing.
- **A fact surgically removed from the artifact**, which leaves it a strict
  subset -- the "behind" direction, which passes. Unfixable while the asymmetry
  holds: "the artifact is missing A->B" and "a concurrent merge added A->B" are
  the same observation from the gate's side. What bounds it instead is the
  **drift ceiling**: the gate fails if the committed model is more than 25%
  behind a regeneration -- which no single merge approaches (three weeks of
  merges produced 2.5% / 5.8%) but months of neglect does. Counts print on
  every run, pass or fail.
- **Node attributes** (signature, doc, attrs, `source.line`). Measured before
  rejecting: of 1,353 shared node ids differing from a regeneration, 1,343
  differed ONLY in `source.line`, because editing a file shifts every
  declaration below it. Gating that is byte-equality wearing a hat.
- **Edge attributes**, same reason at smaller scale.
- **Order**, which `TestCommittedModelIsSorted` covers separately.

One operational caveat before you debug a red gate: a node disappears when the
type-checker stops seeing a declaration, so if a red gate names symbols you did
not touch, suspect the environment (a Go toolchain bump, a tagged build) before
the code. The extractor fails loudly on a per-package load error rather than
silently emitting less.

The model is written **compact, on one line**. Pretty-printing it produced a
1.26M-line file whose one-time reorder GitHub could not diff at all -- the API
returned *"this diff is taking too long to generate"*, which fails the `changes`
job and blocks the PR. So do not read it as a diff; the gate above is what
tells you whether it is right.

### Regenerate the platform graph

```bash
make platform-graph
```

`cmd/platformgraph` (root module: it reads `component/node`, the proto
descriptors, the concept registry and the automation loader, none of which
this base-tier package may import) writes `embedded/platform.graph.json`, one
node or edge per line, sorted, with no timestamp, no absolute path and hosts
written against `<domain>`. Eight passes: **nodes** (the roles and the
packages each role's binary links, `go list -deps -tags <type>` pinned to
linux/amd64 with cgo off), **deploy** (`deploy/k8s/base` plus
`components/engine-bff`, read directly -- any kustomization key but
resources, namespace and labels is refused), **services** (the proto
descriptors, and `serves` from each role to the servers its build
constructs), **frontdoor** (the generated cloud front door), **routing**
(`node.RoutingRules()`), **concepts** (`@relationship` edges by namespace),
**automations** (`automations.FlattenLoopGraph`, the projection the
`automationGraph` builtin's rows and `cmd/memql-arch` share) and **os**
(`component/memql/os_navigation.json`).

The root package's `TestPlatformGraphIsNotStale` (`make platform-graph-check`)
is this model's gate copied: every node and relationship the committed graph
asserts must survive a regeneration, and it may be at most 25% behind one.
`TestPlatformGraphIsWellFormed` holds the committed bytes to the canonical form,
a size ceiling and per-kind floors; `TestPlatformGraphRolesAreTheRoleTable`
holds its roles to `component/node/roles.go` exactly. Regenerate after
changing a role, a manifest in the deploy base, a proto service, the front
door, a routing rule, a concept, an automation or the OS navigation.

### Consume the graphs from another component

```go
import (
    "github.com/znasllc-io/memql/component/architecture/embedded"
    "github.com/znasllc-io/memql/component/architecture/model"
)

m, err := embedded.Load()               // the architecture model
if err != nil { ... }
pg, err := embedded.LoadPlatformGraph() // the platform graph
if err != nil { ... }
ix := model.NewIndex(m)

// L1 -> L2 enumeration
for _, root := range ix.Roots() {
    for _, svc := range ix.Children(root.ID) {
        // ...
    }
}
```

### Annotate a function for observability

```go
//memql:observe verbose redact=password
func (h *Handler) Login(ctx context.Context, user, password string) (err error) {
    ...
}
```

The extractor stamps `observe_level: "verbose"` and `redact_args: "password"` onto the Method node's Attrs, and the observe runtime honors the redact list.

## What's deliberately out of scope here

- **Rendering.** The graphs are the IR. The docs' Mermaid generator (memql#5728) and the OS's Cluster map are renderers, and live elsewhere.
- **Runtime instrumentation.** That's `component/observe`. The bridge is the ID format.
- **DSL concept schemas and SQL migrations.** The model includes Go and the DSL automation trigger graph, and the platform graph the concepts and their relationships -- not their fields; concepts and hypertable schemas for the observability side live in `dsl/observability/` and `component/database/memory-nodes/migrations/`.
